# MOPAN 기술 보고서 — 측정이 고른 검색 파이프라인

**부제: 참조형 한국어 문서 위의 RAG에서, 무엇을 만들었고 무엇을 기각했으며 왜 그랬는가**

2026-09-06 기준(§11·§12는 2026-09-12~13 추가). 이 문서의 모든 수치는 저장소의 평가 하네스(`scripts/eval_retrieval.py`)로
배포 설정에서 실측한 값이거나, 그렇게 실측했던 기록(설계 문서·커밋 메시지·코드 주석)을
그대로 옮긴 것입니다. 재현 명령은 부록 A에 있습니다.

---

## 초록

MOPAN은 사용자가 문서 분류·MCP 도구·모델·워크플로우를 직접 등록하고 조합하는 범용 RAG
플랫폼이다. 개발 과정에서 우리는 하나의 원칙을 고정했다: **모든 단계는 만들기 전에 재고,
낸 값으로만 채택하며, 기각된 시도도 결과로 기록한다.** 이 보고서는 그 원칙 아래 진행된
비교 실험들을 정리한다. 채택된 것은 문자 bigram 스파스 검색(융합 anchor 0.846→0.962),
문서 성격 인식과 조상 문맥 청킹(핵심 청크 dense 순위 91→1), 접기 융합(crossref anchor
0.880→0.920), 파일명 기반 문서 간 인용 해소와 역방향 준용 걷기(문서 간 간선 0→363개),
전달 시점 섹션 머리 부착(구어체 anchor 0.100→0.500)이다. 기각된 것은 문장 단위 색인,
LLM 재순위, 상시 질의 확장, 전역 관련성 하한선, 문서별 상한, 후보 깊이 확대, 투표
합산형 그룹 융합, Doc2Query식 스파스 필드 확장, 문서빈도 기반 토큰 선별, 그리고 전용
그래프 데이터베이스(GraphRAG)다. 각 기각에는 그 시도가 실패한 **기전**을 함께 적는다 —
같은 시도를 다시 하게 될 때 어디서부터 다른지 알 수 있도록.

## 1. 문제 설정

### 1.1 대상 문서의 성격

예시 코퍼스는 한국 특허·상표 심사 문서 13건, 19,704청크다. 이 코퍼스는 일반적인 RAG가
전제하는 "어디서 잘라도 혼자 서는 산문"이 아니다.

1. **참조 의존성.** 법령·심사기준은 반복을 피하려고 **일부러 불완전하게** 쓴다.
   상표법 §36①의 4호("지정상품 및 … 상품류")에는 "상표등록출원서"도 "제36조"도 없다 —
   질문이 임베딩될 문장이 청크 안에 하나도 없다. 지배절은 세 청크 앞에 있다.
2. **문서 간 참조.** "실용신안에 관하여는 「특허법」 제3조부터 제7조까지 … 를
   준용한다" — 답의 절반이 다른 문서에 있고, 준용 선언 자체는 조문 번호의 나열이라
   질문과 겹치는 어휘가 없다.
3. **표 구조.** 유사상품 심사기준(9,070청크)은 산문이 아니라 분류표다. 임베딩할 문장이
   없는 상품명 나열이 류·유사군코드 머리 아래 수십~수백 청크로 이어진다.
4. **어휘 격차.** 사용자는 "치킨집", "어플", "동네 마트"라고 치고, 문서는 "한식점업",
   "애플리케이션 소프트웨어", "슈퍼마켓업"이라고 인쇄한다. 코퍼스는 "어플"이라는
   문자열을 한 번도 쓰지 않는다.
5. **교착어.** 한국어는 조사가 명사에 붙는다. 공백 토크나이저에서 문서의
   `상표등록출원이나`는 질의의 `상표등록출원`과 절대 매칭되지 않는다.

### 1.2 방법론 원칙

이 프로젝트는 상수를 버그에 맞춰 튜닝했다가 결론이 뒤집힌 경험이 세 번 있다(대표적으로
`SPARSE_WEIGHT=0.5` — 파서가 깨진 텍스트를 저장하던 시절의 스파스 성적에 맞춘 값이었고,
파서를 고치자 1.0이 옳았다). 그 뒤로 다음을 규칙으로 굳혔다.

- **만들기 전에 잰다.** 한 번에 한 단계만 바꾸고 같은 픽스처로 누적 측정한다.
- **모든 단계는 독립적으로 끌 수 있고, 끄면 비용이 0이다.** "끈다"는 것은 호출 경로에
  없다는 뜻이지, 입력을 그대로 돌려주는 껍데기 객체가 자리를 지킨다는 뜻이 아니다.
  (실제 사고: `NoneReranker`가 네 호출부에 배선되어 파이프라인이 몇 주 동안 완성된
  것처럼 읽혔다. 삭제했고, 금지했다.)
- **평균이 숨기는 실패를 그룹으로 쪼갠다.** 전체 지표가 유지돼도 한 그룹이 무너지면
  기각이다.
- **가설이 기각되는 것도 결과다.** 기각 기록은 코드 옆에 남긴다.

## 2. 평가 방법

### 2.1 픽스처

| 그룹 | n | 무엇을 보는가 |
|---|---|---|
| `base` | 21 | 심사기준 일반 질문 |
| `neighbor` | 8 | 규칙 청크 + 다음 청크의 단서("다만") 쌍 |
| `tokenizer` | 8 | 조사 접합 불일치(맨명사↔굴절형 양방향) |
| `proviso` | 10 | 단서 조항이 답을 뒤집는 경우 — anchor는 **단서 문장** |
| `crossref` | 25 | 코퍼스 내부 준용·참조 2-hop — anchor는 두 번째 hop |
| `statute` | 14 | 법령 원문 질의 |
| `colloquial` | 10 | 구어체·비전문가 어휘("치킨집 차리는데…") — 별도 픽스처 |

모든 질문은 **사람이 실제로 칠 문장**이다(최소 4어절, 중앙값 10). 맨 키워드 질의는 한
건도 없다 — 일어나지 않는 질의 모양에 상수를 맞추면 그것이 네 번째 "버그에 맞춘
튜닝"이 된다.

### 2.2 지표: recall이 아니라 anchor

주 지표는 **anchor@N — 답을 담은 문장이 모델에게 도달했는가**이다. 페이지 단위
recall은 실패를 놓친다: 실측 사례에서 594쪽의 이중부정 서술이 hit로 잡히는 동안
그것을 평이하게 진술한 593쪽 청크는 도달하지 않았고, 지표는 성공을 보고했는데 답변은
반대였다. anchor는 전달 시점 확장(이웃·인용·섹션 머리)이 붙인 텍스트도 인정한다 —
모델이 읽는 것이 곧 채점 대상이라는 뜻이다.

anchor만 보지도 않는다. **활용률(전달 대비 인용)과 인용된 문장이 실제로 주장을
뒷받침하는지**를 같이 본다. 후보 깊이 20 실험에서 모든 숫자 검사를 통과하면서 상품류
목록을 지어낸 실행이 있었다(§3.6). 그 뒤로 "인용은 세지 말고 읽는다"가 규칙이다.

### 2.3 측정 자체의 함정 — 두 번 데인 기록

1. **하네스가 아무도 돌리지 않는 설정을 쟀다.** `eval_retrieval.py`가 `.env`만 읽고
   `app_settings` 오버라이드를 무시해서, 보고된 모든 수치가 배포와 다른 구성의
   것이었다(0.962라고 알던 값의 실제 배포값은 0.865). 지금은 실행마다 첫 줄에 배포
   구성을 찍는다.
2. **간선 기반 지표는 그래프의 커버리지를 잰다.** 문서 간 간선을 만든 뒤에도 crossref
   픽스처는 0.920에서 움직이지 않았다 — 픽스처의 gold가 코퍼스 내부 2-hop으로 설계돼
   있어 문서 간 도달을 채점할 수 없기 때문이다. 문헌도 같은 경고를 한다: 인용 검증
   지표는 모델이 아니라 그래프 커버리지를 측정한다(arXiv 2606.00898 — 같은 응답이
   그래프 밀도에 따라 환각률 0.79↔0.99로 뒤집힘). 그래서 §6의 검증은 픽스처가 아니라
   라이브 전달 내용의 판독으로 했다.

## 3. 검색 파이프라인 — 단계별 비교와 판정

파이프라인: 질의 → (dense ∥ sparse) → RRF 융합(+접기) → top-N → 인용 부착 → 섹션 머리
→ 이웃 확장 → (약하면) 재작성 재시도 → (그래도 약하면) 되묻기.

### 3.1 스파스 팔: 토크나이저가 스코어러보다 크다

`content_tsv`가 공백 분리(`simple`)이던 시절 스파스 단독 anchor@14는 0.673,
tokenizer 그룹에서 0.375였다. 망가진 팔은 돕지 못하는 데 그치지 않고 **밀어냈다**:
RRF에서 sparse 1위(1/61)는 dense 6위(1/66)를 무조건 이기므로, tokenizer 그룹 융합이
dense 단독(0.875)보다 낮았다(0.750).

토크나이저와 스코어러를 분리해 2×4로 쟀다(스파스 단독 anchor@14):

| 토크나이저 \ 스코어러 | ts_rank (IDF 없음) | BM25 |
|---|---|---|
| 공백(어절) | 0.673 | 0.731 |
| 규칙 조사분리 | 0.808 | 0.885 |
| **문자 bigram** | **0.904** | 0.942 |
| 형태소(kiwi) | 0.923 | 0.962 |

**판정: bigram + ts_rank 채택.** 토크나이저 교체(+0.231)가 스코어러 교체(+0.058)보다
4배 크고, bigram은 새 의존성이 0이며 토크나이저가 6줄짜리 순수 함수다. 형태소는 1문항
차이(유의하지 않음)에 30MB C++ 확장이다. BM25 열은 **상한선일 뿐 배포 불가능하다** —
이 배포의 Postgres(pgvector/pgvector:pg16)에서 생성 가능한 확장은 `pg_trgm`,
`unaccent`, `vector`뿐이라 BM25 확장(ParadeDB, VectorChord)은 선택지가 아니다.
이 제약은 §7에서 다시 중요해진다.

기각된 스파스 후보: 접두 매칭 `:*`(융합 0.793으로 베이스라인 아래), 접두+진짜 BM25
IDF(가설을 직접 구현해 반증 — 문제는 IDF가 아니라 접두 확장이 끌어들인 후보 집합이었다).

### 3.2 덴스 팔

| 모델/단위 | 단독 anchor | 비고 |
|---|---|---|
| 3-small, 청크 (배포) | 0.827 | |
| 3-large@1536, 청크 | 0.904 | Matryoshka — 컬럼 폭 그대로, 마이그레이션 없음 |
| 3-small, 문장 | 0.827 | tokenizer 그룹 0.875→0.750 |
| 3-large, 문장 | 0.885 | proviso 1.000, tokenizer 0.500 |

**판정: 3-small 유지.** bigram이 융합 anchor를 천장(0.962, 당시 픽스처)까지 끌어올린
뒤라 3-large는 anchor를 못 올리고 정밀도만 올렸다(0.228→0.253). anchor를 못 올리는
변경에 재임베딩($0.121)을 시키지 않았다. 수치는 남겨 두었고, 코퍼스가 바뀌면 다시 잰다.

**문장 단위 색인 기각의 교훈:** 29문항에서는 이겼고(0.828→0.897) 52문항에서 졌다
(0.904→0.885). 표본 아티팩트였다. 재측정하지 않았으면 잘못된 결정을 배포할 뻔했다.
단, 그룹별로 보면 원 가설(긴 창의 임베딩이 정밀한 법조문을 희석한다)은 **맞았다** —
proviso 0.900→1.000. 문제는 짧은 단위가 tokenizer 그룹에서 더 크게 잃는 것
(0.875→0.500)이었고, 올바른 수정은 검색 단위 우회가 아니라 인제스트의 구조 인식
청킹이었다(§4).

### 3.3 융합과 그 상수들

RRF k=60(도메인 전반의 경험값, 튜닝하지 않음), sparse 가중 1.0(버그에 맞춰 0.5로
튜닝됐다 되돌아온 이력이 있어 재측정 없이 건드리지 않음). 동점은 부동소수점 1ulp가
아니라 명시적 첫-등장 순서로 깬다 — 질의 확장이 켜지면 랭킹이 2N개가 되어 "안정
정렬이 알아서 해준다"는 전제가 깨지기 때문이다.

### 3.4 재순위: 구현했고, 쟀고, 껐다

LLM listwise 재순위(후보 20): anchor 변화 0, 정밀도 +0.003, 질문당 +1.2초와
$0.00078. 후보를 40으로 늘리면 재순위 **없이는** 0.962→0.904로 떨어지고 재순위로도
0.923까지만 회복 — 최선의 재순위 구성이 공짜 베이스라인보다 낮다. **기본 OFF**
(`RERANK_MODEL=""` = 단계가 호출 경로에 없음).

### 3.5 질의 확장: 단계가 아니라 재시도

상시 확장(N=3): anchor 동일, 정밀도 0.228→0.221, 질문당 +3.8~10초. crossref가
움직이지 않은 이유가 진단적이다 — 2-hop을 못 찾는 원인은 질문 표현이 아니라 두 번째
hop이 첫 번째와 어휘를 공유하지 않는 것이고, 그것은 다른 질문을 던져도 같다.

**판정: 첫 패스는 절대 확장하지 않고, 약한-근거 판정이 켜진 질문에서만 재시도로
확장한다.** 답할 수 있는 질문에서 비용이 정확히 0이 되는 구조다(그 판정이 기본
픽스처에서 0번 발화한다). 부작용 수정 하나: 확장이 켜지면 근거-합의 신호가 원 질의의
순위만 읽어 "합의 없음"으로 오판하던 버그(재작성 질의가 slot 1, 임계값의 4배로
올려놓은 근거를 되묻기가 버렸다)를 변형 전체에 걸친 집합으로 고쳤다.

### 3.6 후보 깊이: 10이 옳고, 늘리면 지어낸다

top_n=5 고정, 전체 코퍼스:

| candidate_limit | recall | anchor |
|---|---|---|
| **10 (배포)** | **0.846** | **0.865** |
| 20 | 0.827 | 0.788 |
| 40 | 0.808 | 0.788 |

깊게 파면 두 팔이 **중위권에서 합의한** 후보(높은 RRF 합산)가 한 팔이 1위로 찍은 진짜
답을 밀어낸다. 더 나쁜 것: 깊이 20 실행이 모든 숫자 검사를 통과하면서 상품류 목록을
**지어냈다**. 이 관측은 §5의 overfetch 기각에서 같은 모양으로 재현된다 — 이
파이프라인에서 "더 많이 가져오기"는 일관되게 손해였다.

같은 이유로 **전역 관련성 하한선도 기각**했다: 무언가를 실제로 걷어내는 임계값
(0.0160~0.0170)은 전부 진짜 답도 함께 걷어냈다(3~7문항 손실). 픽스처의 모든 질문이
답 가능해서 하한선의 이득이 구조적으로 보이지 않는다는 한계까지 적어 두고, 실제 실패
사례(무관 코퍼스 질문)는 §8의 되묻기가 잡는다.

**문서별 상한(per-document cap)도 구현했다가 지웠다.** "한 문서가 top-k를 독점한다"는
가설을 cap=2로 구현해 쟀더니, 문제의 질문에서 융합 후보 **전부가 이미 한 문서**였다 —
올려줄 다른 문서의 후보가 애초에 없어 cap이 아무것도 바꾸지 못했다. 아무것도 하지 않는
단계를 "만들었다"고 남기는 것은 금지이므로 지웠다.

## 4. 문서 구조 인식 — 청킹은 문서 성격이 정한다

### 4.1 세 가지 성격, 두 단계 선택

컬렉션은 **어휘**(프리셋: 편/장/절/관/조/항/호/목 정규식, 인용 패턴)만 공급하고, 그
어휘를 실제로 쓰는지는 **문서가 내용으로 답한다**: 파싱 직후 레벨 마커 비율과 인용
비율을 세서 self_contained / reference_dependent를 문서 행마다 판정하고, 판정과
확신도(high/ambiguous/none)를 화면에 그대로 렌더링한다. 조용한 자동 판정은 이
프로젝트가 한 번 출시했다 걷어낸 실패다(도메인 정규식이 코드에 하드코딩되어 다른
사용자의 문서에서는 아무 일도 하지 않았다). **추론된 것은 보여야 한다.**

### 4.2 검출이 답할 수 없는 것 — override가 장식이 아닌 이유

특허·실용신안 심사기준은 모양으로는 명백한 참조형(spine 0.017, cite 0.383)이지만,
계층으로 재단하자 recall이 **0.923→0.769**로 떨어졌다. 조문 자체가 아니라 조문을
군데군데 인용하는 실무 편람이라, 항 마커 대부분이 인용된 조문의 파편이었고 거기서
자르면 편람의 서술이 조각났다. 소유자가 숫자를 들고 판정을 화면에서 뒤집었고
(self_contained로 재정의), 그 덮어쓰기는 재처리에도 살아남으며 자동 판정과 나란히
표시된다. 같은 모양의 상표심사기준은 반대 결과를 냈다 — 핵심 청크의 dense 순위가
**91→1**로 올랐다. 내용의 모양만으로는 결정할 수 없는 것이 남는다는 사실을 숨기지
않는 것이 이 설계의 형태다.

### 4.3 조상 문맥은 색인 시점에 굽는다

계층으로 잘린 각 조각의 앞에 조상 경로 한 줄을 붙여 **그 텍스트를 임베딩한다**.
"3. 상표 / 4. 지정상품 …" 조각이 "제3장 … > 제36조(상표등록출원) ① …" 머리를 달고
나면, 질문이 찾을 어휘가 전부 같은 청크 안에 있다. 전달 시점에 다시 붙이지 않는 이유:
색인이 이미 한 일을 런타임에 반복하는 것은 같은 텍스트에 두 번 돈을 내는 것이다.
분류표는 같은 수를 머리문장으로 썼다 — 마커에서 합성한 한 문장("상표 출원 시 ~의
상품류는 제43류…")이 대상 청크의 dense 순위를 **1,398→175**로 옮겼고, 이것이 참조형
문서에 같은 접근을 적용해도 된다는 최초의 증거였다.

## 5. 접기 융합 — 야심이 측정에 깎여 정확해진 사례

### 5.1 관찰: 표를 나눠 갖는 형제와 슬롯을 겹쳐 쓰는 사본

"치킨집 차리는데 가게 이름을 상표로 등록하려면 어느 류로 내야 하나요?"의 실측:
정답 섹션 [제43류/S120602]의 조각들이 dense **35·44·55·93위** — 넷이 표를 나눠 가져
후보 10 안에 하나도 못 든다. 같은 융합 상위 10에는 제34조① 사본 2개, 제55조 사본
3개(법령 원문 + 두 심사기준의 인용)가 슬롯을 겹쳐 쓴다. 융합 단위가 청크라서 생기는
두 문제이고, 프로덕션 검색엔진들이 다양성 개입을 사후 제거가 아니라 랭킹 1단계에
두는 이유와 같다(Vespa result-diversity 문서).

### 5.2 스윕: 세 가지 야심의 기각

그룹 키는 색인이 이미 저장한 것을 재사용한다(계층: 문서+경로, 표: 문서+섹션 마커 —
새 컬럼도 재색인도 없음). 키가 문서 범위인 것이 평행 조문 안전장치다: 특허법 제105조와
실용신안법 제27조는 문면이 동일해도(실측 4클러스터) 절대 합쳐지지 않는다.

| 구성 | ALL anchor | crossref | statute | proviso recall |
|---|---|---|---|---|
| 끔 (베이스라인) | 0.872 | 0.880 | 0.786 | 0.800 |
| 조 단위 + 합산2 + 깊이 5배 | 0.814 | 0.800 | 0.643 | 0.600 |
| 항 단위 + 합산2 + 깊이 5배 | 0.814 | 0.760 | 0.714 | 0.600 |
| 항 단위 + 합산1 + 깊이 5배 | 0.860 | 0.840 | 0.786 | 0.600 |
| **항 단위 + 합산1 + 깊이 1배** | **0.884** | **0.920** | 0.786 | 0.800 |

세 기각의 기전:

1. **멤버 점수 합산(cap≥2)은 구조적 편향이다.** 그룹 키가 있는 청크(법령·표)만 점수가
   부풀고 prose 근거가 밀려난다 — proviso recall 0.800→0.600이 그 값이다.
2. **깊이 확대(overfetch)는 §3.6의 재현이다.** 두 팔이 중위권에서 겹친 후보가 한 팔
   1위의 진짜 답을 이긴다.
3. **조 단위 접기는 너무 굵다.** 항을 묻는 질문에 같은 조의 다른 항이 대표로 나간다
   (statute 0.786→0.714).

살아남은 것은 가장 소박한 형태 — **자연 깊이 안에서, 같은 주소의 사본·형제를 접어
겹친 슬롯만 해방한다.** 그것만으로 crossref가 0.880→0.920: 해방된 슬롯이 정확히
상호참조의 두 번째 hop이 잘리던 자리였다. 근거-합의 판정도 그룹 단위가 됐다 —
dense가 섹션의 한 조각을, sparse가 같은 섹션의 다른 조각을 찾으면 이제 합의다.

## 6. 인용 그래프 — GraphRAG를 다시 기각하고, 대신 간선을 진짜로 만들었다

### 6.1 전용 그래프 기술의 기각 근거

외부 조사(2026-09-05)를 우리 실패 세 가지에 대고 정리했다:

- **LightRAG**: 인덱싱이 청크마다 LLM 엔티티 추출을 요구한다. 우리는 인용 관계를
  정규식으로 공짜로 얻는 도메인이다 — 이미 가진 것의 비싸고 부정확한 재구현. 법률
  벤치마크(CAIL)에서도 23.1로 RAPTOR(30.5)·LegalGraphRAG(40.9)에 밀렸다.
- **RAPTOR**: 푸는 문제가 "긴 서사의 흩어진 정보 통합"이지 명시적 참조 해소가 아니고,
  요약 노드는 법령 인용 근거로 쓸 수 없다.
- **Microsoft GraphRAG**: 증분 갱신 시 커뮤니티 재구성 비용 — 법령은 계속 개정된다.
- 가장 우리와 닮은 실측(한국 소방법령 QA, arXiv 2604.06173): 인용 그래프를 재랭킹
  보너스로 쓴 이득이 **Recall@50 +1.78pt**. 그래프 DB를 새로 깔 근거로는 부족하고,
  **이미 있는 간선 표에 역방향을 얹는 비용에는 충분하다** — 그리고 허브 페널티가
  없으면 "제1조 목적"류가 결과를 재독점한다는 경고를 남겼다.

판정: Postgres `chunk_edges` + 재귀 CTE 유지. 간선 추출은 결정론적 정규식(LLM 없음 —
문서당 비용 0, 실행마다 동일, 감사 가능).

### 6.2 발견: 문서 간 간선이 0개였다

역방향을 얹으려고 열어 보니 **해소된 문서 간 간선이 정확히 0개**였다. 인용 패턴이
법명(「특허법」)을 캡처하지 못해 준용 선언의 모든 인용이 미해소로 남아 있었다. 설계
문서는 문서 간 해소를 "문서↔법령 동일성 표가 근거 없는 추측이라" 보류했었지만, 법령
8건이 코퍼스에 들어온 지금 동일성은 추측이 아니라 **파일명**이다("특허법
시행규칙.html" → 특허법시행규칙).

세 층으로 만들었다:

1. **법명 스코프 파싱.** 낫표 제목 뒤의 조문 인용은 그 법의 것이고, 스코프는 다음
   낫표 또는 "이 법"에서 끝난다. 리셋이 필요한 실측 문형: "…「특허법」 제64조에 따라
   출원공개되거나 **이 법** 제21조제3항에 따라…" — 리셋이 없으면 제21조가 특허법
   것으로 붙는다. 잘못된 조문은 없는 조문보다 나쁘다(같은 원칙이 문서 안 모호 규칙에도
   적용된다: 같은 경로를 두 조문이 열면 어느 쪽에도 잇지 않는다).
2. **파일명 해소 + 최장 접두 규칙.** 같은 제목의 문서가 둘이면 모호로 잇지 않는다.
3. **역방향 걷기 + 허브 페널티.** 선택된 청크를 인용하는 **다른 문서의** 청크를 최대
   1개 붙인다. 피인용 8곳 초과(허브)는 아예 붙이지 않고, 인용자 중에서는 나가는 간선이
   많은 쪽(준용 선언은 조문 번호의 목록이다)을 고른다.

결과: 순차 재적재 후 문서 간 간선 **363개**(실용신안법 212, 실용신안법 시행령 110 —
준용의 법다운 분포).

### 6.3 실패에서 배운 것: 동시 재적재 경쟁

법령 8건을 **동시에** 재적재하자 3건이 FK 위반으로 실패했고, 성공했던 문서의 문서 간
간선도 대상 문서의 청크 교체가 CASCADE로 **행째** 지웠다(재적재 직후 실용신안법
간선 0개 실측). 수정 세 겹: dst FK를 SET NULL로(간선의 주인은 인용하는 문서 — 대상이
사라지면 "미해소"로 돌아가야지 기록이 사라지면 안 된다), 삽입 직전 dst 생존 검증,
그리고 문서가 색인될 때 자기를 법명으로 가리키는 남의 미해소 간선을 도로 잇는
`relink_external`(간선의 target_path에 "법명#경로"를 남겨 두는 것이 열쇠). 인용하는
문서가 먼저 업로드되는 순서와 재적재로 비워진 경우가 같은 길로 회복된다.

### 6.4 검증: 픽스처가 아니라 판독으로

crossref 픽스처는 움직이지 않았다 — §2.3의 오라클 함정 그대로, gold가 문서 간 도달을
채점하지 못한다. 검증은 라이브 전달의 판독으로 했다: 실용신안 심사 질문에서 준용 선언
청크(실용신안법 §15)가 검색되어 특허법 §57·§58 **전문을 데리고** 도착하고, 역방향
부착(`cited-by:「실용신안법」 제15조`)도 확인됐다. 문서 간 해소가 생기기 전에는 이
전달이 구조적으로 불가능했다.

## 7. 구어체 격차 — 두 번 기각하고 세 번째가 이겼다

구어체 픽스처의 출발점: recall 0.500, **anchor 0.100**, 10문항 중 8건이 되묻기로 이탈.
유일한 다리는 되묻기 게이트 뒤의 비결정적 LLM 재작성이었다(배포형 재시도 포함 0.200).

### 7.1 기각 1: Doc2Query식 스파스 필드 확장

문헌의 처방(Doc2Query++, arXiv 2510.09557 — 확장문은 dense에 섞지 말고 스파스 인덱스에만,
"dual-index")을 그대로 구현했다: 분류표 931개 섹션마다 구어체 표현을 오프라인 생성해
(gpt-4o-mini, 총 $0.124) 그 섹션 모든 청크의 `content_tsv`에만 넣었다. content와
embedding은 그대로, 생성 어휘는 metadata에 남겨 감사 가능하게.

**결과: 0.500/0.100 그대로. 완전 무효.** 원인 진단이 이 실험의 실제 수확이다 —
실패는 커버리지가 아니라 **랭킹**이었다. 정답 청크에 "할인마트"가 실제로 들어갔는데도
sparse 순위 300위 밖: IDF 없는 ts_rank 아래에서 질의의 흔한 bigram(상표·등록·이름…)이
수천 청크와 겹치며 희귀 신호가 익사한다. 적용분은 backfill로 되돌렸고, 스크립트는
기각 기록과 재도전 조건("스파스 점수 함수가 IDF를 갖게 된 다음")을 달아 남겼다.

### 7.2 기각 2: 문서빈도 기반 토큰 선별(가난한 IDF)

점수 함수를 못 바꾸면 **후보 선택**을 바꾸자는 시도: 렉심별 DF 표를 만들고, 전체
청크의 일정 비율보다 흔한 질의 토큰을 tsquery에서 뺐다(임계 0.02/0.05/0.10 스윕).

**결과: anchor 무변동.** 생존 토큰의 실측이 기전을 보여준다 — "동네 마트 이름을
상표로 등록하려는데…"에서 살아남은 것은 `나요`, `는데`, `록하`("등록하려는데"의 조각)
같은 **활용 어미의 bigram 파편**이고, 정작 `마트`는 흔하다고 잘렸다. **bigram 위에서
DF는 희귀성 신호가 못 된다** — 내용어의 bigram은 흔하고 어미의 bigram은 희귀할 수
있다. 부수 효과(스파스 지연 300→43ms, 되묻기 이탈 8→4)는 실측이므로 코드와 표는
기본 꺼짐으로 남기고, 형태소 토크나이저로 갈아탈 때 다시 잰다. 참고로 형태소(kiwi)
스파스 팔 자체도 구어체에서 0.100이었다 — 토크나이저 단독으로는 이 격차를 못 닫는다.

### 7.3 채택: 섹션 머리의 전달 시점 부착

두 기각을 지나 문항별 판독을 하자 다른 그림이 보였다: **접기 융합 이후 검색은 이미
절반의 문항에서 정답 섹션의 조각을 1~3위로 가져오고 있었다.** 실패의 자리는 검색이
아니라 전달이었다 — 질문에 실제로 답하는 "상품/서비스업의 범위 ◦…" 줄은 섹션의 **첫
조각**에 살고, 대표로 뽑히는 것은 질의와 어휘가 겹친 다른 조각이며, ±1 이웃 확장은 몇
조각 떨어진 머리에 닿지 못한다.

처방: 배달된 조각과 같은 (문서, 섹션)의 첫 조각이 배달되지 않았으면 그 본문을
붙인다(`attach_section_heads` — 이웃·인용과 같은 계약: 정체 불변, content만 자람,
예산은 전체 근거 집합의 천장). 재설계 문서가 "류·유사군 머리글을 상품 목록에 붙여야
한다"고 재청킹 과제로 적어 둔 것의 **전달 시점 판본**이고, 재색인 비용이 0이다.

| 구성 | 구어체 recall | 구어체 anchor |
|---|---|---|
| 이전 (첫 패스) | 0.500 | 0.100 |
| 이전 (배포형, 재시도 3) | 0.500 | 0.200 |
| **+ 섹션 머리 (첫 패스)** | 0.500 | **0.500** |
| **+ 섹션 머리 (배포형)** | 0.500 | **0.600** |

기본 픽스처 86문항은 전 그룹이 그대로다(ALL 0.884, crossref 0.920). 비용은 문항당
약 +1,400 컨텍스트 토큰. 남은 절반(recall 0.500)은 진짜 검색 도달 문제이고, 그
처방은 §10의 향후 과제(형태소 + 파이썬 BM25 재점수)다.

### 7.4 이 절의 교훈

세 시도의 순서가 거꾸로였다면 — 판독을 먼저 했다면 — 두 기각은 없었을 것이다. 하지만
두 기각이 남긴 진단(랭킹 실패의 기전, bigram-DF의 무의미함)은 향후 과제의 방향을
좁혔고, 그 기록이 없었다면 다음 사람이 같은 벽을 다시 쌓았을 것이다. 기각을 기록하는
이유가 이것이다.

## 8. 근거가 약할 때: 지어내지 않고 되묻는다

막다른 길("관련 문서가 없습니다")과 날조 사이의 세 번째 길로, 검색이 실제로 돌려준
것(융합 점수, 두 팔의 합의)으로 약함을 판정하고, 약하면 **재작성 재시도 → 그래도
약하면 되묻기**를 순서대로 탄다. 되묻기는 새 UI가 아니라 평범한 답변이고, 후보 질문은
검색 결과에서 유도하며 지어내지 않는다. 질의 길이로는 판정하지 않는다 — 짧지만 잘
구성된 질문은 멀쩡하고, 길지만 막연한 질문이 문제다. 오탐률을 같이 잰다: 답변 가능한
기본 픽스처에서 되묻기 이탈은 0/52여야 하고, 실제로 그렇다.

구어체에서는 여전히 8/10이 이 게이트에 걸린다. 게이트 완화(`WEAK_EVIDENCE_RRF_SCORE`)
는 정확도-회피 트레이드오프라 소유자의 값으로 남겼다 — 단, §7.3 이후 되묻기가
제시하는 후보 질문의 질이 눈에 띄게 좋아졌으므로(도달한 근거에서 유도되므로) 이대로가
나은 사용자 경험일 수 있다는 관찰을 함께 남긴다.

## 9. 표를 읽는 두 갈래 — 정확 조회 도구와 행 묶음 임베딩

표형 자료는 이 파이프라인의 실측된 약점이었다. 상품분류표(마커 행 8,167건)가 코퍼스에
멀쩡히 있는데도, 복합 장문 질의에서 분류표 청크가 후보 순위 경쟁에 밀려 0건이 되는
현상을 같은 날 세 질의로 잡았다(17:42 hit 5건 / 19:40 miss 0건 / 19:49 hit 6건 —
`condensed_query` 비교로 입증). 원인은 커버리지가 아니라 랭킹이다: 짧은 코드 행과
자연어 질문은 벡터 공간에서 멀고, 동질적인 행 수천 개는 서로 뭉쳐 변별력이 없다.
처방은 랭킹을 더 고치는 것이 아니라 **표만 다른 길로 읽는 것**이었다.

### 9.1 정확 조회 MCP — "RAG 문서 표 조회" (동봉·기본 제공)

임베딩을 경유하지 않고 `chunks`를 SQL 정확 부분일치로 읽는 MCP 도구(`table_lookup`)를
동봉했다. `[코드/코드]` 마커 절을 먼저 찾아 행 단위로 결정적으로 돌려주고(실측:
"소셜네트워크" → 제38류 전자게시판제공업 + 제45류, "치킨" → [제29류/G0703]), 남는
슬롯은 전 코퍼스 본문 일치로 채운다. 키 컬럼은 판단하지 않는다 — 행 주변 텍스트를
통째로 돌려주고 어떤 값이 코드인지는 답변 모델이 문맥으로 읽는다. 이것이 임의의 표에
일반화되는 이유다.

폴백 합산은 실사고가 만들었다: 처음에는 마커 일치가 있으면 본문을 안 봤는데,
"사파이어"가 상품분류표의 보석 행에 먼저 걸려 방금 임베딩한 등록농약 표의 살균제
사파이어가 **0건**이 됐다. 두 세계에 다 있는 말은 흔하므로, 마커 일치 후 남는 슬롯을
본문 일치로 채우게 바꿨다(합산 후: 분류표 2건 + 본문 2건). 도구는 부팅 시 자동
등록되는 기본 제공(builtin, DELETE 409 거부)이고 risk=read라 자동 숙고 경로를 바로
탄다.

### 9.2 표 파일 임베딩(xlsx·csv) — 행 직렬화와 행 묶음 청킹

엑셀을 그대로 올리는 길을 열면서, 각 행을 `컬럼명: 값 | 컬럼명: 값` 한 줄로
직렬화했다. 행이 컬럼 이름을 스스로 들고 다니므로 정확 조회의 반환 창 안에서 키 컬럼
추측 없이 값이 읽히고, 임베딩에도 자연어가 붙는다. 한국 엑셀의 "CSV로 저장"이 내놓는
cp949는 utf-8-sig 다음 순서로 시도하며, 둘 다 아니면 뭉개는 대신 거부한다 —
`errors=replace`로 뭉갠 글자는 정확일치가 영원히 못 찾는다.

산문 청킹을 표에 적용한 비용은 실데이터로 쟀다. 공공데이터포털 농약 정보
10,001행(3.9MB cp949 CSV → xlsx)을 일반 컬렉션(무설정)에 올린 결과:

| 청킹 | 청크 수 | 임베딩 토큰 | 원문(2.84M) 대비 | 비용(3-small) |
|---|---|---|---|---|
| 산문(korean_legal 계층, 겹침 창) | 19,994 | 4,931,081 | 1.74배 | ~$0.10 |
| **행 묶음(행 경계 보존, 겹침 0)** | **5,001** | **2,837,659** | **1.00배** | **~$0.057** |

임베딩 **42.5% 절감**, 청크 수 **75% 감소**. 산문 전략은 행을 중간에서 자르고 그
절단을 겹침으로 무마하는데, 행은 서로 독립이라 겹침이 무마할 절단이 없다 — 순수한
낭비였다. 행 묶음은 행 경계를 절대 자르지 않고 `max_chunk_tokens`까지 행을 채운다
(시트가 바뀌면 끊는다). 파일 형식(xlsx·csv)이 행 구조를 보증하므로 이 선택은 내용
휴리스틱이 아니다 — §4가 기각했던 "냄새 맡기"와 다른 이유다.

품질은 회귀가 아니라 개선이었다: 같은 질문("사파이어라는 농약이 있던데 몇 배로
희석해서 쓰는거야?")이 산문 청킹 색인에서는 부분 근거로 clarify(되묻기)에 걸렸고,
행 묶음 색인에서는 answer_agent가 제형별(액상수화제 2000배/과립훈연제)로 정리해
인용 7건으로 직답했다 — 반쪽 행 대신 온전한 행 여러 개가 한 청크에 들어 근거 밀도가
올라간 결과다.

### 9.3 임베딩 429는 장애가 아니라 상태다

만행짜리 표의 첫 색인은 실패했다: OpenAI 분당 토큰 한도(1M TPM)에 429가 쏟아졌고 SDK
내부 재시도(3회, 초 단위 백오프)가 바닥났다. 큰 표를 올린 날의 429는 오류가 아니라
정상 상태라, 임베딩 배치 루프가 `RateLimitError`에 한해 지수 백오프(최대 8회, 45초
상한)로 길게 기다리게 했다 — 429가 아닌 오류는 그대로 실패한다(인내는 한도에만,
장애에는 아니다). 재실측: 429를 수십 번 맞으며 4.93M 토큰을 완주해 indexed로 끝났고,
거절된 요청은 과금되지 않으므로 추가 비용은 0이다.

## 10. 한계와 향후 과제

1. **구어체 recall 0.500.** 어휘 격차의 나머지 절반은 스파스 점수 함수의 IDF 부재다.
   측정된 상한(형태소+BM25 0.962, §3.1)은 있고 배포 경로(파이썬 재점수)는 없다. 다음
   슬라이스의 1순위. bigram-DF의 실패 기록(§7.2)을 먼저 읽을 것.
2. **statute 그룹 실패 3건** — 스파스 팔이 무관한 청크로 채워지는 것. 1과 원인이 같다.
3. **crossref 픽스처는 문서 간 도달을 채점하지 못한다**(§2.3). 문서 간 gold를 가진
   픽스처 확장이 필요하다 — 단, 그래프 커버리지를 재는 함정을 피해서.
4. **relink는 간선만 되살리고** 인용하는 문서 화면의 해소 숫자는 옛 값으로 남는다.
5. **parent 간선은 기록만 되고 아무 데도 읽히지 않는다.** 쓰거나 지우거나.
6. 낫표 없는 관례("법 제X조" = 모법)와 브래킷 별칭([특법54])은 문서별 별칭 설정이
   필요해 다루지 않았다 — 도메인 지식은 코드가 아니라 설정으로.
7. 평가 질문 대부분이 한 도메인(특허·상표)에서 나왔다. 다른 도메인 코퍼스가 들어오면
   전부 다시 재야 한다.
8. **멀티턴 요약의 품질은 재지 않았다**(§11.5). 되묻기 왕복이 긴 상담 로그 픽스처가
   필요하다.
9. **값싼 단계(압축·게이트·숙고)의 소요 시간이 추적에 없다**(§12.2). 강등이 8초를
   조용히 먹어도 화면은 모른다. 단계별 ms를 `trace`에 남길 것.

## 11. 멀티턴 기억 — 버퍼와 롤링 요약

2026-09-12 추가. 이 절만 검색 픽스처가 아니라 대화 흐름의 문제를 다룬다.

### 11.1 문제: 열 메시지 앞은 존재하지 않았다

답변 프롬프트는 `messages` 표에서 최근 10개(질문·답변 5쌍)를 원문으로 실었고 그 앞은
읽지 않았다. 세 가지가 조용히 어긋났다.

1. **절벽.** 되묻기 왕복 두 번 뒤의 본 질문이 열한 번째 메시지가 되는 순간, 모델은
   사용자가 처음에 무엇을 하려 했는지 모른 채 답했다. 대화 화면에는 다 보이므로
   사용자는 모델이 왜 딴소리를 하는지 알 수 없다.
2. **기아.** 예산(`ANSWER_CONTEXT_TOKEN_BUDGET` 8,000)은 근거를 먼저 채우고 남는 만큼
   이력을 실었다(§3.6의 "근거가 답보다 중요하다"는 결정의 부작용). 근거 14개가 예산을
   다 먹으면 이력은 0개 - **직전 턴조차** 사라졌다.
3. **압축기의 근시.** 후속 질문을 자립형 검색어로 다시 쓰는 압축기(`condense.py`)와
   도구 숙고(`mcp/auto.py`)는 여섯 턴·턴당 500자만 봤다. 되묻기가 그보다 앞이면
   "그거"는 풀리지 않았다.

### 11.2 후보와 판정

| 방식 | 판정 | 이유 |
|---|---|---|
| 슬라이딩 창(현행) | 기각 | 고정 비용은 장점, 창 밖은 소리 없이 사라진다. 짧은 거래형 대화용 |
| 전체 이력 원문 | 기각 | 8K 예산에서 근거와 정면 충돌, 긴 상담은 아예 안 들어간다 |
| 전체 요약만 | 기각 | 직전 턴의 어투·세부(숫자, 조건)가 요약에서 뭉개진다 |
| **버퍼 + 롤링 요약** | **채택** | 최근 턴 원문 + 오래된 턴 요약. 업계가 수렴한 모양 |
| 대화 이력 벡터 검색(장기 기억) | 보류 | 대화 하나 안의 문제엔 과하다. 대화 간 기억이 필요해질 때 |

버퍼+요약은 LangChain의 `ConversationSummaryBufferMemory`, LangGraph의 요약 노드,
OpenAI Agents SDK의 세션 compaction, Claude Code의 auto-compact가 전부 같은 형태로
쓰는 패턴이다([참고 문헌](#116-참고-문헌)). 순수 슬라이딩 창은 열 턴을 넘기면 가장
약한 선택이라는 데 조사한 자료가 일치했다.

### 11.3 설계

- **원문 창** `HISTORY_WINDOW_MESSAGES` = 8(최근 네 턴). 조사한 권고(3~4턴)와 맞추되
  운영 설정으로 열어 둔다.
- **롤링 요약** `conversations.summary` + `summary_through_at`(마이그레이션 0023).
  창 밖으로 밀려난 메시지가 4개(두 턴) 이상 쌓이면 값싼 모델
  (`CONVERSATION_SUMMARY_MODEL`, 비면 질문 다시 쓰기 모델)이 "현재 요약 + 새 턴 →
  갱신된 요약"을 쓴다. 1,500자 상한, 사용자 목표·확정된 사실과 숫자·되묻기와 그 답·
  미해결 사항을 남기고 인사말과 반복은 버린다. `summary_through_at` 뒤의 메시지만
  새로 접으므로 한 번 빠져도 다음 턴이 이어받는다(멱등).
- **갱신 시점**: 답변 저장 뒤 백그라운드 태스크. 조사한 프레임워크는 대부분 다음 호출
  앞에서 동기로 요약하지만, MOPAN은 답이 `done` 프레임 하나로 도착하므로 그 앞에 요약
  호출을 두면 사용자가 그만큼 더 기다린다. 요청과 분리된 태스크라 클라이언트가 끊어도
  끝까지 간다. 프로세스가 죽으면 같이 죽는데, 멱등이라 다음 턴이 메운다 - 큐(arq)는
  그때 가서 옮긴다.
- **싣는 자리**: 요약은 시스템 프롬프트 끝에 "참고용 요약" 꼬리표를 달고 붙는다.
  버퍼+요약 구현들이 공통으로 두는 자리이고, lost-in-the-middle 곡선의 앞자리
  (primacy)라 짧은 요약이 잊히지 않는다. 그 뒤로 원문 턴 → 근거 울타리 → 질문 순서는
  그대로다(가장 신선한 근거가 질문 바로 앞, recency 자리).
- **불신 등급**: 요약은 사용자 발화를 읽은 모델 출력이다. 근거와 같은 규칙으로 울타리
  표식(`<<END EVIDENCE …>>`)을 지워 싣는다 - 요약 안의 문장이 울타리를 일찍 닫을 수 없다.
- **이력 최소 몫** `HISTORY_RESERVE_TOKENS` = 1,500. 근거 채우기가 이 몫 앞에서 멈춘다.
  몫은 실제 이력 비용과 예약값 중 작은 쪽이라, 이력이 한 줄이면 근거를 공연히 깎지
  않는다. 예산 8K에서 근거 우선이라는 §3.6의 결정은 유지되고, "직전 턴이 0개"만 막는다.
- **압축기·도구 숙고**도 같은 요약을 시스템 프롬프트에 받는다. 창이 비어 있어도(전부
  요약으로 접힌 긴 대화) 압축기가 동작한다.
- **추적**: 답변마다 `trace.memory`에 요약 글자 수, 받은 이력 수, 실제로 실린 원문 턴
  수가 남는다. "모델이 이 대화의 무엇을 봤는가"를 사후에 답하기 위해서다.

### 11.3a 실대화에서 잡힌 두 가지 (같은 날)

MOPAN API로 7턴을 실제로 돌렸다(gemma4:26b, vLLM). 2턴째에 앱 이름 '모임톡'과 출시 시기를
말하고 7턴째에 "내 앱 이름과 출시 시기가 뭐였지?"를 물었다.

1. **요약 문구.** 요약(434자, '모임톡'·'내년 3월' 포함)이 시스템 프롬프트에 실렸는데도
   모델은 "제공된 문서에 없다"고 답했다. 요약 블록을 "참고용"이라고만 적었더니 답변
   프롬프트의 "근거에 없으면 없다고 말하라"가 요약까지 덮은 것이다. 블록을 "[Conversation
   memory] 이미 나눈 말이지 문서가 아니다, 앞서 논의한 것에 대한 질문은 근거 없이 여기서
   답하라, [n]으로 인용하지 말라"로 고치자 "앱 이름은 '모임톡', 출시 예정은 내년 3월"로
   답했다. 요약을 싣는 것과 모델이 그것을 쓰게 하는 것은 다른 일이다.
2. **경합.** 6턴째 답이 오자마자 1초 뒤 보낸 7턴째는 요약 0자로 답했다(추적 기록
   `memory.summary_chars=0`). 백그라운드 갱신(3~9초)이 끝나기 전에 대화를 읽은 것이다.
   다음 턴은 제 대화의 갱신이 돌고 있으면 상한 10초까지 기다렸다가 읽는다
   (`memory.await_inflight`). 사람의 타자 속도에서는 거의 항상 이미 끝나 있다.

### 11.3b 대화를 넘는 사용자 기억 (2026-09-13 추가)

§11의 요약은 대화 하나 안에서만 산다. "새 대화를 열어도 기억하나?"(소유자)에 답이 "아니오"
였고, 필요하다고 해서 ChatGPT의 '메모리'와 같은 모양으로 붙였다(`app/chat/user_memory.py`,
표 `user_memories`, 마이그레이션 0024).

- **무엇을**: 사용자에 관한 오래 가는 사실만 - 누구인지(직무·소속), 무엇을 하는지(프로젝트·
  제품명·날짜), 답을 받는 방식의 선호, 스스로 말한 제약. 질문 자체·문서 내용·어시스턴트의
  답·인사말은 아니다. 한 줄 300자, 계정당 50줄(넘치면 오래된 것부터), 한 턴에 최대 4줄.
- **언제**: 매 턴 뒤 백그라운드에서 값싼 모델이 "현재 기억 + 이번 턴의 사용자 발화(+답 앞
  400자)"를 보고 새 사실만 낸다. 이미 있는 사실(표현만 다른 것 포함)은 모델에게도 금지하고
  코드에서도 정규화해 거른다. 실패는 "기억 그대로".
- **어디에**: 답변 시스템 프롬프트의 "[About the user]" 블록, 최신 것부터 2,000자 안에서.
  요약과 같은 불신 등급으로 울타리 표식을 지우고 "데이터"라고 못 박는다. 압축기·도구
  숙고에는 싣지 않는다(아직 필요가 없다).
- **경계**: `user_id`로만 읽고 쓴다. `/api/memory`는 본인 것만 돌려주고, 남의 id로 지우면
  존재 여부도 흘리지 않는 404다. 관리자도 남의 기억은 못 본다(경로에 사용자 id가 없다).
  계정 삭제 시 함께 지워진다. 계정 창의 "내 기억"에서 한 줄씩·전부 지운다.
- **실측**: 새 계정으로 "농촌진흥청 데이터 사업, '모임톡' 상표 출원 준비, 내년 3월 출시,
  답은 표로" 한 턴 → 4줄 추출(e4b, 수 초) → **새 스레드**에서 "앱 이름·출시 시기·근무처?"
  → 셋 다 맞고 표로 답했다.
- **안 잰 것**: 잘못 기억한 사실의 비율(과잉 추출). 상한과 삭제 화면이 안전장치이지 측정은
  아니다. 설정: `USER_MEMORY`(끄면 뽑지도 싣지도 않는다), `USER_MEMORY_MODEL`.

### 11.4 비용

두 턴마다 값싼 모델 호출 한 번(입력 ≤ 요약 1,500자 + 새 메시지 4개 × 2,000자 상한).

## 12. 2026-09-12~13 변경 총람 — 답이 왜 이렇게 빨라졌나

소유자 관찰(09-13 0시): "답변이 어마어마하게 빨라졌다". 저장된 답변 기록(`messages`의
`retrieval_ms`·`latency_ms`)으로 전후를 재고, 원인을 셋으로 나눈다. 체감의 대부분은
**vLLM이 아니라 사라진 8초**에서 온다.

### 12.1 저장된 기록의 전후 (gemma4:26b, 답변 4건씩)

| | 검색·준비 p50 | 모델 호출 p50 | 합계 p50 | 출력 토큰 평균 | 생성 속도 |
|---|---|---|---|---|---|
| 전 (09-09, Ollama) | 9,402 ms | 8,404 ms | 19,717 ms | 1,780 | 162 tok/s |
| 후 (09-13, vLLM) | 282 ms | 2,629 ms | 2,894 ms | 523 | 205 tok/s |

표본이 넷씩이고 질문도 다르므로 "6.8배"라는 숫자 자체를 믿지는 말 것. 대신 두 열이 따로
말하는 것을 읽는다: 검색·준비가 9.4초에서 0.3초로, 모델 호출이 같은 속도 기준으로 26%
빨라졌다.

### 12.2 원인 1 — 값싼 단계의 8초 타임아웃이 사라졌다 (가장 크다)

질문마다 답변 전에 값싼 모델 호출이 최대 셋 돈다: 후속 질문 압축(§11), 의도 게이트,
도구 숙고. 셋 다 `QUERY_EXPANSION_MODEL=gpt-4o-mini`였고, OpenAI 잔액이 소진된 동안 이
호출은 429를 받았다. openai SDK는 429를 재시도 대상으로 보고 지수 백오프로 세 번 다시
부르는데, 그 사이 MOPAN의 8초 상한(`QUERY_EXPANSION_TIMEOUT_SECONDS`)이 만료되어 "원문
강등"으로 끝났다. 계약대로 답변은 나갔지만 **모든 질문이 조용히 8초를 먼저 버렸다**
(로그: 강등 경고 7건, `credit_balance_exhausted` 16건). 화면에는 아무 표시가 없어 "원래
느린가 보다"로 보였다.

09-12 결제 뒤 같은 호출이 0.2~0.4초에 끝난다. 검색·준비 p50 9,402→282ms가 그것이다.
같은 부류의 앞선 실사고가 09-09의 콜드 로드(§ 메모 `ollama-keep-alive-cold-load`: 의도
분류기 e4b가 5분 뒤 내려가 있다가 로드 8초를 넘겨 강등)였고, 그날 저녁 keep_alive=-1로
막았다. 즉 09-09 표본의 9.4초에는 두 원인이 겹쳐 있다.

교훈: **강등은 안전하지만 공짜가 아니다.** 실패가 "원문 그대로"로 조용히 끝나는 설계는
답의 정확도를 지키는 대신 지연을 숨긴다. 추적 화면에 값싼 단계별 소요 시간을 남기는 것이
다음 과제다(§10에 추가).

### 12.3 원인 2 — 답변 모델을 vLLM으로 (§ docs/local-llm-concurrency.md)

같은 노드·같은 요청으로 잰 통제 비교(입력 1,123토큰, 출력 256):

| 동시 | Ollama 슬롯 4 | vLLM |
|---|---|---|
| 1 | 1.9 s | 0.9 s |
| 8 | 7.5 s | 1.1 s |
| 16 | 13.4 s | 1.8 s |
| 64 | - | 2.0 s (4,884 tok/s) |

한 사람 기준으로 2배, 여럿이면 자릿수가 다르다. 한 사람에서도 빨라진 이유:

- **접두사 캐시.** 답변 시스템 프롬프트(수천 자)는 모든 요청의 접두사다. vLLM은 그 KV를
  재사용한다(운영 149요청에서 적중률 69.9%). Ollama는 요청마다 다시 읽었다.
- **BF16.** Ollama는 GGUF Q4_K_M, vLLM은 BF16 원본이다. B200에서는 양자화가 속도 이득이
  없고 정밀도만 잃는다.
- **사고 끄기의 명시.** MOPAN은 추론 모델로 표시되지 않은 로컬 모델에 `reasoning_effort:
  none`을 보내고 vLLM은 이것을 `enable_thinking=false`로 옮긴다. 생각 토큰이 앞에 붙지
  않는다.
- **상주.** vLLM은 프로세스와 함께 살아 콜드 로드가 없다.

### 12.4 원인 3 — 같은 날 함께 바뀐 것 (속도와 무관하지만 답의 내용이 달라진다)

- 멀티턴 기억(§11): 최근 8개 메시지 원문 + 대화별 롤링 요약. 이력 몫 1,500토큰을 근거보다
  먼저 떼어 둔다 → 프롬프트가 커졌다(입력 평균 3,237→5,102토큰). 커졌는데도 빨라진 것은
  접두사 캐시 덕이다.
- 요약 모델은 로컬 `gemma4:e4b`(Ollama, 8.9초/회, 백그라운드라 대기에 안 든다).
- 설정 화면 "대화 기억" 탭, 추적 기록 `trace.memory`.
- 모바일: 앱 셸을 시각 뷰포트에 맞춤(키보드 위 입력창), 음성 입력 뒤 자판.
- Ollama의 `gemma4:26b`는 내렸다(vLLM이 대신). `.env VLLM_BASE_URL`, `scripts/start_vllm.sh`.

### 12.5 되돌리기와 주의

- vLLM을 끄면(또는 죽으면) `gemma4:26b`는 자동으로 Ollama로 돌아가되, 이제 Ollama에
  고정하지 않으므로 첫 요청이 콜드 로드(수 초)를 문다.
- OpenAI 잔액이 다시 소진되면 12.2가 그대로 재발한다. 징후는 화면이 아니라
  `retrieval_ms`가 8초 근처로 뛰는 것이다. 압축·게이트 모델을 로컬 e4b로 돌리면 잔액과
  무관해진다(품질은 재지 않았다).

OpenAI·Gemini·Perplexity·Claude의 딥 리서치와 STORM·gpt-researcher·LangChain Open Deep
Research를 조사했다(§13.6). 공통 골격은 "범위 확정 → 계획(사용자에게 보임) → 병렬 검색 →
격차 루프 → 인용 강제 종합 → 내보내기"이고, 이 앱에 맞게 고른 것은 다음이다.

- **범위 확정(scoping)**: Gemini의 "계획을 보여 주고 승인" 대신, 첨부한 계획서에서 목표·대상·
  방법·산출물·핵심어를 먼저 뽑아 카드로 보여 준다. 중복성 검토의 "질문"은 사람의 한 줄이
  아니라 계획서 자체이므로 되묻기 대화보다 이것이 맞다.
- **관점(sub-query)을 계획 시점에 표시**: 끝날 때까지 숨기지 않는다. 지금까지는 `sub_queries`가
  완료 시에만 저장됐다.
- **닫힌 인용**: 읽은 근거 번호만 출처가 되는 기존 계약(`cited_numbers`)을 유지했다. 문헌이
  말하는 "프롬프트만으로는 인용이 새는" 문제의 처방이 이미 있었다.
- **판정은 참고**: NTIS 차별성 검토와 iThenticate가 공통으로 다는 단서 - 최종 판단은 심사위원 -
  를 중복성 방의 보고서 위에 단다.
- **PDF는 서버에서**: 브라우저 인쇄는 iOS에서 앱 화면이 찍힌다(원본 CR-67 실사고). Playwright는
  Chromium 300MB, WeasyPrint는 CJK 폰트 함정이 보고돼 있어 원본의 fpdf2 렌더러를 그대로 가져왔다
  (표 머리글 다음 장 반복, 행 분리 금지, 나눔고딕).

### 13.3 파이프라인 (후)

```
첨부 있음 → 0. scoping: 계획서 앞 16,000자 → {title, goals, targets, methods, outputs, prior_work, keywords}
1. planning: 요청 + 검토 대상 요약(+방의 관점 힌트) → 검색 관점 N개 (즉시 저장·표시)
2. searching: 관점마다 top_k, 청크 병합
3. gap: 수집 근거 요지 → 보완 관점 ≤3 → 재검색 (rounds)
4. synthesis: 문서별로 묶은 근거 [n] + "요청 / 검토 대상 요약 / 첨부 본문" → 지침(=시스템 프롬프트) + 인용·형식 규칙
5. done → PDF (본문 + 출처 부록)
```

### 13.4 실측 (같은 계획서, 같은 방, gpt-4.1 종합·gpt-4o-mini 계획)

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 보고서 구조 | 요청 요약 / 확인된 내용 / 한계 (범용) | 검토 대상 요약 → 비교 문서 적합성 → 유사 기존 연구 → 항목별 중복성 → 계승·발전 → 취약 부분 → 세부과업 조정안 → 개선방향 종합표 → 대안 → 수정 문안 → 종합 판정 (지침 그대로 12절) |
| 인용 | 6건 | 10건 |
| 소요 | 33초 | 27초 |
| 검토 대상 요약 | - | 목표 2·대상 2·방법 2·산출물 3·핵심어 9 |

코퍼스가 특허 심사기준이라 "상표 지정상품 자동 분류 시스템" 계획서로 흐름을 검증했다.
농업 완결보고서(RAG/2016~2020)를 넣기 전까지 진짜 중복성 판정의 품질은 재지 못한다 - 그것이
이 절의 한계다.

### 13.5 화면

- 방 목록: 템플릿 배지(중복성 검토), "보고서 N건".
- 새 방: 템플릿 카드 먼저(중복성 검토·신규과제 발굴·계획서 초안·빈 방) → 이름·설정.
- 방: "중복성 검토 시작" 카드(계획서 첨부가 주역, 요청문은 선택) → 지침 한 줄 요약 + "지침
  보기·편집"(전용 창: 본문 전체, 글자 수, 템플릿으로 바꾸기, 버전 이력·현행으로) → 보고서 목록
  → 방 설정(관점 힌트 추가, 지침은 여기 없음).

## 14. 워크플로우 에디터 — 네 노드와 편집 도구

2026-09-13. 소유자: "분기 기능 정도만 있다. 보통 이런 워크플로우엔 뭐가 있는지 리서치해서 만들어라.
모바일 UI가 왜 이러냐."

### 14.1 업계 조사 요지

Dify·Coze·Flowise·Langflow·n8n·Copilot Studio·OpenAI Agent Builder를 봤다(§14.5). 노드 어휘는
Dify가 가장 RAG 친화적이다 - Start, LLM, Knowledge Retrieval, Question Classifier, IF/ELSE, Code,
Template, Variable Aggregator, Iteration, Parameter Extractor, HTTP Request, Tool, Answer. 편집기
공통은 undo/redo, 노드 검색, 단축키, 노드별 입출력을 보여 주는 인라인 실행, 초안/게시 버전.
**모바일에서 그래프를 편집하게 만든 제품은 없다** - 전부 데스크톱 전용이고, 폰은 실행 로그와
배포된 챗을 보는 용도다.

### 14.2 채택한 것

| 노드 | 하는 일 | 다음 노드가 읽는 값 |
|---|---|---|
| 모델 호출(llm) | 프롬프트(템플릿)로 모델을 한 번. 구조화 항목을 적으면 JSON. 근거로 넘길지 선택 | `text`, 항목들 |
| 질문 분류(classify) | 갈래 중 하나로 분류하고 그 갈래의 간선만 연다 - 분기의 다중 버전 | `category`, `label` |
| 정보 추출(extract) | 글에서 항목(글·수·예/아니오)을 뽑는다. 없으면 비움 | 항목 이름들 |
| 텍스트 조합(template) | 앞 노드 값들을 글 하나로. 비용 0, 즉시 | `text`, `length` |

편집기: 되돌리기/다시하기(Ctrl+Z / Ctrl+Shift+Z), 복제(Ctrl+D), 저장(Ctrl+S), 실행해보기와 추적 화면에 모델·텍스트 노드의 **출력 앞부분** 표시.
모바일: 왼쪽에 세로로 쌓이던 아이콘 레일(햄버거와 겹쳐 보이던 것)을 아래쪽 이름 달린 막대로,
도구 서랍·노드 설정·실행해보기 패널은 아래에서 올라와 화면을 거의 다 쓰는 시트로. 자동 정렬은
만들었다가 뺐다 - 노드가 위아래로 이어지는 그림이라 가로 열 맞춤이 필요 없었다(소유자).

안 만든 것과 이유: **HTTP 요청**(SSRF - MCP 서버 등록이 같은 일을 권한 경계 안에서 한다),
**코드**(샌드박스 없이는 안 된다), **반복(iteration)**(웨이브 실행기에 하위 그래프 개념이 없다 -
필요가 생기면 `workflow:` 호출을 항목마다 도는 노드로), **변수 병합**(답변 노드가 이미 모든
근거를 모은다).

### 14.3 설계에서 지킨 선

- **템플릿 치환은 프롬프트·본문에서만.** 도구 인자의 템플릿 금지(`expr.py`)는 "인자 스키마가
  무엇인지 말할 수 없게 된다"는 논거였다. 모델이 읽을 글에는 그 논거가 닿지 않으므로 허용하되,
  참조 하나가 끌어오는 글자는 8,000자로 자른다.
- **모델 노드는 도구 노드와 같은 계약.** 웨이브(병렬)로 돌고, 호출 상한을 도구 호출과 함께
  세고, 실패는 노드 하나의 failed이지 죽은 실행이 아니다. 분류 실패는 어느 갈래도 열지 않는다
  (분기가 조건을 못 풀면 양쪽을 자르는 것과 같은 규칙).
- **분류 간선은 갈래 id를 `when`으로 갖는다.** 분기의 참/거짓과 같은 자리라 실행기·재개(승인 뒤)
  경로가 그대로 쓰인다.
- **eval은 여전히 없다.** 모델의 JSON은 `json.loads`로만 읽고, 갈래 id는 정해진 목록과 대조한다.

### 14.4 실측

라이브 API로 "질문 분류 → (규정: 핵심어 추출 → 문서 검색 / 잡담: 모델 호출) → 답변" 그래프를
만들어 두 질문을 넣었다(gemma4:26b, vLLM).

| 질문 | 경로 | 시간 |
|---|---|---|
| 유사군코드는 어떻게 부여되나요? | 분류 «규정 질문» → 추출 «상표 출원 시 유사군코드 부여 방식» → 검색 → 답변(인용 2) | 16.4s |
| 안녕? 오늘 기분 좋다! | 분류 «잡담» → 모델 호출 «…행복해지는 기분이야!» → 답변 | 0.3s |

두 경로 모두 안 간 쪽은 skipped로 기록됐고, vLLM의 `response_format: json_object`가 분류·추출의
JSON을 정확히 냈다. 테스트 8건(`tests/test_workflow_nodes.py`) + 기존 엔진 82건 통과.

## 15. 임베딩 서빙을 vLLM으로 — 코퍼스가 작을 때 바꾼 이유와 측정

2026-09-13 낮. 감시 폴더로 완결보고서·RFP 12,107건(31GB) 색인을 시작하니 병목이 임베딩이었다:
Ollama qwen3-embedding(4 슬롯, GPU 1 80%)으로 6건/분, 전체 약 33시간. GPU 0은 비어 있었고
색인된 문서가 105건뿐이라, 임베딩 백엔드를 바꾸려면 지금이 가장 싼 시점이었다(소유자가 판단을
맡겼다).

### 15.1 무엇을 바꿨나

| | 전 | 후 |
|---|---|---|
| 서버 | Ollama 11434 (GGUF Q4_K_M, 슬롯 4) | vLLM 0.26 pooling 8003, GPU 0 (BF16, 연속 배칭) |
| 모델 이름 | qwen3-embedding:8b | 같음(`--served-model-name`) - EMBEDDING_MODEL·프로필·카탈로그 불변 |
| 차원 1536 | 서버의 `dimensions` | vLLM은 `dimensions`를 400으로 거절 → 프로바이더가 앞 1536차원을 잘라 정규화(MRL, 같은 연산) |
| 설정 | - | `EMBEDDING_BASE_URL`(비면 예전처럼 Ollama) |

`scripts/start_vllm_embed.sh`가 띄우고 start_local.sh가 부른다. 모델 존재 확인은 Ollama의
/api/tags가 404면 /v1/models로 본다(`local_model_present`).

### 15.2 측정

- **재임베딩**: 청크 26,338개(≈948만 토큰)를 **188초**. vLLM이 보고한 프리필 27,656 tok/s.
  Ollama였으면 약 1시간.
- **검색 품질**(같은 87문항 픽스처, 같은 코퍼스, 워커 정지 상태에서 전후 측정):

| 행 | 전(Ollama Q4) anchor | 후(vLLM BF16) anchor | recall 전/후 |
|---|---|---|---|
| dense만 | 0.713 | 0.701 | 0.655 / 0.644 |
| **hybrid(배포 경로)** | **0.747** | **0.747** | 0.655 / 0.655 |

배포 경로는 동일하다. dense 단독의 1문항 차는 잡음 범위(§2.3의 기준)다. statute 그룹이 0.133인
것은 두 측정 모두 같다 - 이 노드의 코퍼스에 법령 8종이 아직 안 들어 있어서이며, 이 전환과
무관하다.

### 15.3 색인 속도와 두 가지 실사고

| 구성 | 건/분 | 병목 |
|---|---|---|
| Ollama 임베딩, 워커 1(동시 10) | 6 | GPU 1 임베딩 80% |
| vLLM 임베딩, 워커 1(동시 10) | 15 | CPU 파싱 - 워커 프로세스 하나가 102%(GIL) |
| vLLM 임베딩, 워커 1(동시 24) | 7 | 로드 90: OCR 풀 24×16 tesseract × OpenMP 스레드 |
| vLLM 임베딩, 워커 3(동시 8, OCR 4, OMP 1) | 19 | 워커 셋 각 100% |
| **vLLM 임베딩, 워커 8(동시 8, OCR 4, OMP 1)** | **67** | GPU 0 임베딩 83% - 다시 GPU 쪽 |

파싱은 anyio 스레드라 프로세스 하나의 GIL을 나눠 쓴다 - 동시 수를 올려도 한 코어다. 처리량은
프로세스 수로 늘어난다(같은 큐를 여러 arq 프로세스가 나눠 먹는다). 12,107건은 약 3시간.

세 번째 실사고: 워커 8개가 128건 배치를 쏟자 vLLM 임베딩 큐에 **2,101 시퀀스**가 줄을 섰고,
120초 안에 차례가 안 온 요청이 "Connection error"로 실패해 문서가 failed로 남았다(37건).
임베딩은 멱등이라 클라이언트 타임아웃 900초·재시도 3으로 기다리게 하고, 프로세스당 동시 문서를
8→6으로 낮췄다(8×6=48). 처리량은 어차피 GPU 0 임베딩(83~96%)이 상한이다.

그 과정에서 잡힌 실사고 둘:

1. **스캔 크론이 굶었다.** 2분 크론은 잘 들어갔지만(Redis에 스캔 잡 24개) 본 워커의 슬롯이 전부
   문서 처리라 하나도 돌지 못했다 - arq 큐는 선입선출이고 우선순위가 없다. 500건짜리 첫 스캔 뒤
   등록이 멈춘 이유. 스캔은 제 큐(`arq:watch`)에서 제 워커(`WatchWorkerSettings`, 동시 1)가
   돈다. 관리자 '지금 스캔'도 그 큐로 간다. start_local.sh가 워커 둘을 띄운다.
2. **워커 재시작이 문서를 죽인다.** 재시작 때 진행 중이던 잡은 취소되고(SIGTERM) 시도 2회를 다
   쓴 문서는 failed로 남는다("문서를 처리하지 못했습니다", 원인은 임베딩 Connection error =
   취소된 요청). 색인 중에는 워커를 재시작하지 말고, 했다면 failed 문서를 uploaded로 되돌려
   다시 큐에 넣는다(이번 색인에서 그렇게 했다).

네 번째: 색인이 끝나고 보니 실패 352건 중 **296건이 Postgres의 "invalid byte sequence for encoding
UTF8: 0x00"** - 글꼴 매핑이 깨진 PDF의 추출 텍스트에 NUL이 섞여 나오고 text 컬럼이 거부한다.
파서마다 고치지 않고 파이프라인 한 곳(`rag/blocks.py:sanitize`)에서 NUL과 C0 제어문자를 지운다
(개행·탭은 남긴다). 나머지는 처리 시간 초과(870초)와 진짜 깨진 파일이다.

### 15.4 남은 것

- Ollama의 qwen3-embedding은 폴백으로 남겨 두었다(EMBEDDING_BASE_URL을 비우면 그대로 돌아감).
  단, 그렇게 돌아가면 벡터 공간이 미세하게 다르므로 다시 `reembed.py`를 돌려야 한다.
- 평가 하네스의 질문 임베딩 캐시는 모델 이름으로만 키가 잡혀 있어 서버를 바꾸면
  `/tmp/mopan-eval/emb-qwen3-embedding_8b.json`을 치워야 한다(이번 측정에서 그렇게 했다).
