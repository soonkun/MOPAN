# Slice 6 — 워크플로우와 슈퍼 에이전트

## 확정된 용어

제품 소유자가 정리했다. **"에이전트"라는 말은 쓰지 않는다.**

| | 워크플로우 | 슈퍼 에이전트 |
|---|---|---|
| 절차를 짜는 주체 | **사람** | **모델** |
| 언제 만들어지나 | 미리, 저장해 둠 | 질문을 받고 즉석에서 |
| 어떻게 부르나 | 입력창에서 `@` | 켜 두면 알아서 |
| 실패 양상 | 절차가 틀렸으면 **항상** 틀림 | 계획이 나쁠 수 있음 |

**둘은 같은 것을 만든다.** 워크플로우 그래프다. 사람이 그리면 저장된 워크플로우,
모델이 그리면 슈퍼 에이전트의 일회성 워크플로우.

### 그래서 실행기는 하나다

이 문서의 이전 판에는 실행기가 둘이었다 — 플래너 기반과 결정적. 소유자의 정리
(*"슈퍼에이전트를 활성화하면 알아서 워크플로우를 만들어 돌리는걸로"*)가 그것을
없앤다. 플래너의 출력이 `ExecutionPlan`이 아니라 **워크플로우 그래프**가 되면,
실행기·추적·화면이 전부 하나로 합쳐진다.

부수 효과로 얻는 것: 슈퍼 에이전트가 방금 만든 워크플로우를 **캔버스에 그대로 열어
고치고 저장**할 수 있다. 자율 실행이 저작 도구의 입력이 된다.

---

## 1. 통합 Tool 인터페이스

### RAG는 도구 인터페이스를 구현한다. MCP 서버가 되지는 않는다.

소유자의 표현은 *"RAG를 수행하는 MCP"*였고 의도는 맞다 — 플래너와 실행기가 RAG·MCP·
워크플로우를 **똑같이 "부를 수 있는 것"으로 취급**해야 한다.

다만 **MCP는 전송 프로토콜이지 도구의 정의가 아니다.** RAG를 진짜 MCP 서버로 만들면
지금 프로세스 안 함수 호출인 검색(측정 269ms)에 HTTP 왕복·직렬화·인증이 붙는다.
균일함은 인터페이스에서 오지 전송에서 오지 않는다.

```
Tool (ABC)
  name, description, input_schema, risk_level
  async def call(args, *, ctx) -> list[Evidence]

├─ RagTool       프로세스 안. 기존 hybrid_search를 감싼다
├─ McpTool       HTTP 너머. 기존 mcp/client.py를 감싼다
└─ WorkflowTool  저장된 워크플로우를 실행한다
```

**모든 도구가 `list[Evidence]`를 돌려준다.** Slice 1이 만든 이음새이고 이미 세 번
버텼다(첨부 → MCP → 오케스트레이터). `answer()`는 이번에도 바뀌지 않는다. 그것이 이
슬라이스의 합격 기준이다.

`risk_level`은 `mcp_tools` 첫 마이그레이션부터 있다. `RagTool`은 `read`,
`WorkflowTool`은 **그 워크플로우가 부르는 도구들의 최대 위험도**를 물려받는다 —
파괴적 도구를 감싼 워크플로우가 안전해 보이면 안 된다.

## 2. 워크플로우 스키마

### 노드

| 종류 | 하는 일 |
|---|---|
| `input` | 사용자 질문. 그래프당 하나, 삭제 불가 |
| `tool` | 도구 하나를 부른다. RAG·MCP·워크플로우 모두 여기 |
| `branch` | 조건에 따라 나간 간선 중 하나를 고른다 |
| `answer` | 모인 Evidence로 답한다. 그래프당 하나, 삭제 불가 |

`input`과 `answer`가 고정인 이유: 그 둘이 없으면 실행할 수 없고, 지울 수 있게 하면
저장은 되는데 돌릴 수 없는 워크플로우가 생긴다.

### 간선과 변수

간선이 **실행 순서를 정한다.** 지금과 결정적으로 다른 점이다 —
`PlanStep.depends_on`은 순서만 정하고 출력을 넘기지 않는다고 코드 주석에 명시돼 있다.
워크플로우는 넘긴다.

```
[input] → [tool: 특허검색  q={{input.text}}]
              ↓
        [branch: {{특허검색.count}} > 0]
         ├─ 참  → [tool: 심사기준RAG  q={{특허검색.top.title}}]
         └─ 거짓 → [tool: 웹검색      q={{input.text}}]
                        ↓
                    [answer]
```

**참조는 문자열 치환이 아니라 경로 평가다.** 치환이면 도구 출력이 그대로 다음 도구의
인자가 되고, 그 출력은 제3자 서버가 만든 신뢰할 수 없는 데이터다. 경로로 꺼낸 값만
쓰고 인자 스키마로 검증한다.

### 분기 조건 — 구조적 표현식을 먼저

- **구조적**: `{{노드.count}} > 0`. 싸고 예측 가능하다.
- **LLM 판단**: `"결과가 특허 관련이면"`. 유연하지만 **분기마다 모델 호출 = 돈**이다.

**스키마는 둘 다 담고 구현은 구조적부터.** LLM 분기는 `kind: "llm"` 자리를 만들되
켜지지 않는다. 비용이 눈에 보이는 상태에서 소유자가 켜는 것이 맞다.

표현식은 **직접 파싱한다. `eval`은 쓰지 않는다** — 워크플로우는 관리자가 쓰지만 그
값에는 도구 출력이 섞이고 그것은 외부에서 온다. 지원 연산은
`== != > >= < <= 존재함 비어있음`과 `and or not`까지.

### 저장

`workflows` + `workflow_versions`. **버전을 남긴다** — 프롬프트에서 이미 같은 결론에
도달했다. 사람이 절차를 고치다 나빠지면 되돌아가야 하고, `messages`가 어느 버전으로
답했는지 가리켜야 의미가 있다.

**노드 좌표도 저장한다.** 지금 캔버스가 좌표를 저장하지 않는 이유는 `agents`에 넣을
자리가 없어서였다. 사람이 배치한 그림은 다시 열었을 때 그대로여야 한다.

## 3. 입력창에서 `@`로 부르기

소유자가 지목한 형태다 — `@`를 치면 쓸 수 있는 것들의 목록이 뜨고 골라서 쓴다.

목록에 오르는 것은 **부를 수 있는 모든 것**이다: 저장된 워크플로우, MCP 도구, 그리고
RAG 분류. 셋 다 `Tool`이므로 목록도 한 종류다.

- `@`만 치면 전체, 뒤에 글자를 이으면 이름으로 좁힌다
- 고르면 입력창에 칩으로 박히고, 그 질문은 그것을 쓴다
- **한글 IME 중에는 뜨지 않는다.** 조합 중 `@`가 확정되지 않은 상태에서 목록을 열면
  글자가 먹힌다. `isComposing`을 이미 전송 억제에 쓰고 있으므로 같은 신호를 쓴다
- 골라 넣은 워크플로우가 그 사이 지워졌으면 전송 시점에 한국어로 거절한다.
  칩이 남아 있다는 것이 그것이 아직 있다는 뜻은 아니다

## 4. 실행기

`app/workflow/executor.py` **하나**. 저장된 그래프든 슈퍼 에이전트가 방금 만든
그래프든 같은 입력이다.

### 상한 — 계획 없는 실행기는 청구서다

오케스트레이터에서 쓴 방식을 그대로 가져온다.

- 노드 수 상한, 도구 호출 총량 상한
- 전체 벽시계 예산 (`asyncio.timeout`)
- **깊이 제한과 순환 검출** — 워크플로우가 워크플로우를 부를 수 있으므로. 저장 시점에
  정적으로 순환을 거부하고, 실행 시점에 깊이를 세는 이중 방어
- 실패한 노드는 기록하고 계속. 근거가 하나도 안 모이면 답하지 않고 그렇게 말한다
- 벽시계는 **파(wave)마다 하나의 마감**으로 적용한다. 오케스트레이터가 이미 겪었다:
  async generator가 `yield`에서 멈춰 있을 때 타임아웃이 터지면 소비자 태스크가
  취소되어 `CancelledError`가 SSE 스트림을 죽인다

### 관측

`messages.trace`가 이미 JSONB이고 계획이 들어간다. 워크플로우 실행도 **같은 자리**에
들어가고, 화면은 "계획 출처"만 다르게 표시한다(사람 / 슈퍼 에이전트). 추적 화면이
둘로 갈라지면 사용자가 어느 쪽을 보는지 알 수 없게 된다.

## 5. 슈퍼 에이전트 설정의 축소

- 슈퍼 에이전트는 **대화 단위 선택**으로 남는다 (지금 그렇다)
- 그 설정은 **범위 체크**만 한다: 쓸 수 있는 RAG 분류, MCP 도구, 워크플로우
- **`agents.orchestrator` 컬럼은 제거한다.** 이것이 층위를 섞은 범인이다 — "정해진
  절차"가 "자율 계획"을 켜고 있었다. 워크플로우는 정의상 자율 계획이 아니다

## 6. 이름 바꾸기

`agents` → `workflows`. UI만 바꾸고 코드에 `agent`를 남기면 다음 사람에게 지금의
혼동을 그대로 물려준다. 마이그레이션으로 테이블·컬럼·API 경로를 함께 옮긴다.

`AgentTool`이 아니라 `WorkflowTool`인 이유도 같다.

기존 행은 버리지 않는다. 저장된 것마다 동등한 그래프를 만든다:
`input → [tool: RAG(허용 분류)] → answer`, 프롬프트와 모델은 그대로. 허용 도구가
있으면 병렬 `tool` 노드로 붙인다. **동작이 바뀌지 않는 변환**이고, 사용자는 그 뒤에
그 그래프를 편집하면 된다.

---

## 7. 일부러 정하지 않은 것

- **루프.** `for each`는 상한과 비용 모델이 따로 필요하다. 요청되지 않았다.
- **워크플로우 간 공유 상태.** 한 실행 안의 변수만 있다.
- **사람 승인 노드.** 오케스트레이터에 이미 승인 일시정지가 있다(1회용 토큰 + 두 번째
  요청). `risk_level`이 이미 흐르므로 같은 메커니즘을 재사용한다 — 새로 설계할 것이
  없다.

---

## 8. 합격 기준

1. **`answer()`가 바뀌지 않는다.** 바뀌어야 한다면 Slice 1의 이음새가 틀렸다는 뜻이고
   그것대로 알아야 할 정보다.
2. 저장된 워크플로우가 없는 배포는 **오늘과 동일하게 동작한다.**
3. 캔버스에서 순서를 바꾸면 **실행 순서가 실제로 바뀐다.** 지금 캔버스에 적힌 "선을
   그리는 자리는 일부러 두지 않았습니다" 문단은 이때 지운다.
4. 워크플로우의 허용 목록이 실행 중에도 **경계로 남는다.** 그래프가 허용 밖 도구를
   참조하면 **저장 시점에** 거부한다.
5. **슈퍼 에이전트가 만든 그래프와 사람이 그린 그래프가 같은 실행기를 지난다.**
   두 경로가 갈라지면 이 설계의 요점이 사라진다.
